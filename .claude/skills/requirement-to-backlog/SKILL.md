# Requirement → Backlog

รับ requirement ดิบจากผู้ใช้ → เขียนเอกสาร spec → อัปเดต backlog → บันทึก log
เอกสารเขียนเป็น **ภาษาไทย** (คำศัพท์เทคนิคเป็นอังกฤษได้) path ทั้งหมดอ้างอิงจาก root ของโปรเจกต์

## ขั้นตอน

### 1. ทำความเข้าใจ requirement
- อ่าน requirement ดิบ และรายการไฟล์ใน `docs/01-requirements/01-spec/` + `docs/01-requirements/backlog.md` (ถ้ามี) เพื่อดูบริบทเดิม
- ระบุ: เป้าหมาย, ผู้ใช้/บทบาท, ฟีเจอร์ที่ต้องมี, business rules, ขอบเขต (in/out of scope), ข้อจำกัด, เกณฑ์ยอมรับ (acceptance criteria)

### 2. ถามผู้ใช้เมื่อไม่แน่ใจ
- ถ้ามีจุดที่คลุมเครือหรือต้องเดา **ต้องถามก่อนเขียน อย่าเดาเอง**
- ทุกคำถามต้องมี **ตัวเลือก/แนวทางอย่างน้อย 3 แนวทาง** พร้อมข้อดี-ข้อเสียสั้น ๆ และระบุข้อที่แนะนำ (ใส่ "(แนะนำ)") ผู้ใช้ตอบเองนอกตัวเลือกได้
- รวมคำถามที่เกี่ยวข้องไว้ถามพร้อมกัน (ไม่เกิน 4 ข้อต่อรอบ) ใช้ AskUserQuestion ถ้ามี; ถ้าทำงานเป็น sub agent ที่ถามผู้ใช้โดยตรงไม่ได้ ให้หยุดและส่งคำถามกลับไปให้ผู้เรียกในรูปแบบเดียวกัน (ดูหัวข้อ "รูปแบบคำถาม")
- ไม่ต้องถามเรื่องที่ตอบได้จากเอกสารที่มีอยู่หรือมีค่า default สมเหตุสมผล ให้ระบุเป็น assumption ในเอกสารแทน

### 3. วิเคราะห์ความเกี่ยวข้องกับ requirement เดิม
ถ้า requirement อ้างอิงถึงเอกสารที่มีอยู่ (หรือเนื้อหาซ้อนกับ spec เดิม) ให้อ่านเอกสารนั้นแล้วตัดสินใจ:
- **สร้างเอกสารใหม่** เมื่อเป็นฟีเจอร์/หัวข้อแยกชัดเจน หรือเป็นการเปลี่ยนแปลงใหญ่ → ลิงก์ไปเอกสารเดิมในหัวข้อ "เอกสารที่เกี่ยวข้อง"
- **แก้ไขเอกสารเดิม** เมื่อเป็นการแก้เล็กน้อย/เพิ่มรายละเอียดในหัวข้อเดิม → ห้ามสร้างเอกสารซ้ำ
- **แทนที่เอกสารเดิม** → สร้างฉบับใหม่ ย้ายฉบับเก่าไป `docs/00-archived/` (ห้ามลบ) และบอกไว้ในเอกสารใหม่
- สรุปเหตุผลของการตัดสินใจนี้ในเอกสารและใน log ถ้าไม่ชัดเจนให้ถามผู้ใช้ตามข้อ 2

### 4. สร้างเอกสาร requirement
- ที่อยู่: `docs/01-requirements/01-spec/{YYYYMMDD}-{RUNNING_NO}-{SUMMARIZE_TOPIC}.md`
  - `YYYYMMDD` = วันที่วันนี้
  - `RUNNING_NO` = เลขลำดับ 2 หลัก (`01`, `02`, ...) นับต่อจากไฟล์ที่ขึ้นต้นด้วยวันที่เดียวกันในโฟลเดอร์ (ไม่มี → `01`)
  - `SUMMARIZE_TOPIC` = หัวข้อสรุปสั้น ๆ แบบ kebab-case ตัวพิมพ์เล็ก (ภาษาอังกฤษ) เช่น `student-grade-upload`
- ตรวจชื่อไฟล์ว่าไม่ซ้ำก่อนเขียน
- โครงเอกสาร:

```markdown
# {ชื่อ requirement}

- **ID:** REQ-{YYYYMMDD}-{RUNNING_NO}
- **วันที่:** {YYYY-MM-DD}
- **สถานะ:** Draft

## 1. ที่มา / Requirement ดิบ
{ข้อความจากผู้ใช้ ตามที่ได้รับ}

## 2. เป้าหมาย
## 3. ผู้ใช้ / บทบาทที่เกี่ยวข้อง
## 4. Functional Requirements
| ID | รายละเอียด | Priority (Must/Should/Could) |
|----|------------|------------------------------|
| FR-1 | ... | Must |

## 5. Non-functional Requirements
## 6. Business Rules
## 7. ขอบเขต
- In scope:
- Out of scope:

## 8. Acceptance Criteria
## 9. Assumptions และคำตอบที่ได้จากผู้ใช้
## 10. คำถามที่ยังเปิดอยู่
## 11. เอกสารที่เกี่ยวข้อง
{ลิงก์แบบ [[../01-spec/ชื่อไฟล์|label]] ตาม convention ของ docs}
```
- ตัดหัวข้อที่ไม่เกี่ยวออกได้ แต่ห้ามแต่งข้อมูลที่ผู้ใช้ไม่ได้ให้ — ระบุเป็น assumption หรือคำถามที่เปิดอยู่

### 5. อัปเดต `docs/01-requirements/backlog.md`
- ถ้าไฟล์ยังไม่มี ให้สร้างด้วยโครงนี้:

```markdown
# Backlog

รายการงานที่สรุปจาก requirement ใน [[01-spec/index|01-spec]] (อัปเดตโดย skill `requirement-to-backlog`)

| ID | รายการ | Priority | สถานะ | ที่มา (Spec) |
|----|--------|----------|--------|--------------|
```
- เพิ่มหนึ่งแถวต่อ Functional Requirement (หรือกลุ่ม FR ที่ทำเป็นงานเดียวได้): ID รูปแบบ `BL-{YYYYMMDD}-{RUNNING_NO}-{n}`, Priority จาก spec, สถานะเริ่มต้น `Todo`, ที่มาเป็นลิงก์ `[[01-spec/ชื่อไฟล์|REQ-...]]`
- **ห้ามลบหรือเขียนทับแถวเดิม** ถ้า requirement เป็นการแก้ spec เดิม ให้อัปเดตแถวที่เกี่ยวข้อง (หรือเพิ่มแถวใหม่ + แก้สถานะแถวเก่าเป็น `Superseded`)

### 6. บันทึก log
- ไฟล์: `docs/05-log/{YYYYMMDD}-log.md` (วันที่วันนี้) ถ้ามีอยู่แล้วให้ **เพิ่มต่อท้าย** ห้ามเขียนทับ ถ้าไม่มีให้สร้างโดยขึ้นต้น `# Log {YYYY-MM-DD}`
- เพิ่มหัวข้อ `## {HH:mm} requirement-to-backlog: {หัวข้อ}` สรุป: requirement ที่รับ, ไฟล์ที่สร้าง/แก้/ย้าย (เป็นลิงก์), การตัดสินใจเรื่องเอกสารเดิม, คำถามที่ถามและคำตอบ, assumptions, แถวที่เพิ่มใน backlog

### 7. สรุปให้ผู้ใช้
รายงานสั้น ๆ: path ของ spec, จำนวนรายการที่เพิ่มใน backlog, assumptions/คำถามที่ยังค้าง

## รูปแบบคำถาม
```
คำถาม: {ประเด็นที่ไม่แน่ใจ และเหตุผลที่ต้องรู้}
 1. {แนวทาง A} — ข้อดี / ข้อเสีย (แนะนำ)
 2. {แนวทาง B} — ข้อดี / ข้อเสีย
 3. {แนวทาง C} — ข้อดี / ข้อเสีย
 (หรือตอบเป็นแนวทางอื่นได้)
```
