# การเก็บ Log กิจกรรม (Audit Logging)

- **ID:** REQ-20261015-01 (อ้างในข้อความ requirement ว่า REQ-AUDIT)
- **วันที่:** 2026-10-15
- **สถานะ:** Draft

## 1. ที่มา / Requirement ดิบ
> ระบบ Grade Runway ต้องบันทึก Log ของกิจกรรมต่อไปนี้ เพื่อใช้ตรวจสอบย้อนหลัง สืบสวนเหตุการณ์ผิดปกติ และเป็นหลักฐานประกอบการปฏิบัติตาม PDPA
> กิจกรรมที่ต้องลง Log: (1) เข้าสู่ระบบ/ออกจากระบบ/เข้าสู่ระบบไม่สำเร็จ (2) ดูข้อมูลเกรดหรือ GPA ของนักศึกษา (3) ส่งข้อความในแชท (4) อนุมัติ ปฏิเสธ หรือแก้ป้าย "เชิงลบ/ไม่เชิงลบ" ของข้อความ (5) ผู้ตรวจเปิดอ่านข้อความ (6) เปลี่ยนเกณฑ์ความเสี่ยงหรือเกณฑ์คัด Mentor (7) เปลี่ยนสิทธิ์ผู้ใช้ (8) ให้หรือถอนความยินยอม (9) ขอดู แก้ หรือลบข้อมูลส่วนบุคคล (10) เปิดดู Log
> เงื่อนไข: แต่ละรายการต้องมีผู้กระทำ เวลา ผลลัพธ์ และรหัสอ้างอิงของข้อมูลที่เกี่ยวข้อง / Log ต้องไม่เก็บเนื้อหาข้อความแชทหรือค่าเกรดจริง / Log ต้องแก้หรือลบไม่ได้ / ผู้ดู Log ได้คือ admin เท่านั้น และดูได้อย่างเดียว / เก็บ Log 1 ปี แล้วลบอัตโนมัติ / Log ที่มีข้อมูลส่วนบุคคลอยู่ภายใต้ REQ-PDPA ด้วย

## 2. เป้าหมาย
- ตรวจสอบย้อนหลังได้ว่าใครทำอะไรกับข้อมูลใด เมื่อไหร่ และผลเป็นอย่างไร
- สืบสวนเหตุการณ์ผิดปกติ
- เป็นหลักฐานประกอบการปฏิบัติตาม PDPA โดยตัว Log เองต้องไม่กลายเป็นแหล่งรั่วไหลของข้อมูลอ่อนไหว

## 3. ผู้ใช้ / บทบาทที่เกี่ยวข้อง
| บทบาท | เกี่ยวข้องกับ Log อย่างไร |
|-------|---------------------------|
| Admin | ผู้ดู Log เพียงกลุ่มเดียว (อ่านอย่างเดียว) และผู้กระทำในบางเหตุการณ์ (เปลี่ยนสิทธิ์/เกณฑ์) |
| นักศึกษา, Mentor, อาจารย์ | เป็นผู้กระทำ/เจ้าของข้อมูลในเหตุการณ์ต่าง ๆ แต่ดู Log ไม่ได้ |
| ระบบ (system) | ผู้กระทำของงานอัตโนมัติ เช่น ลบข้อมูลครบกำหนดเก็บ |

## 4. Functional Requirements
| ID | รายละเอียด | Priority (Must/Should/Could) |
|----|------------|------------------------------|
| FR-1 | ลง Log ครบ 10 กลุ่มเหตุการณ์ตามตาราง "เหตุการณ์ที่ต้องลง Log" ด้านล่าง | Must |
| FR-2 | ทุกรายการมีฟิลด์: ผู้กระทำ (actor ID + บทบาท), เวลา, ผลลัพธ์ (สำเร็จ/ล้มเหลว), ประเภทเหตุการณ์, รหัสอ้างอิงของข้อมูลที่เกี่ยวข้อง (ref ID) | Must |
| FR-3 | Log ห้ามเก็บเนื้อหาข้อความแชทและค่าเกรด/GPA จริง เก็บได้เฉพาะรหัสอ้างอิง (เช่น message ID, student ID, รหัสรายวิชา) | Must |
| FR-4 | Log เป็นแบบ append-only: แก้ไขหรือลบรายการไม่ได้ผ่านทุกช่องทางของแอป (รวม admin) | Must |
| FR-5 | หน้าดู Log เฉพาะ admin แบบอ่านอย่างเดียว (ไม่มีปุ่มแก้/ลบ/ส่งออกที่แก้ได้) บทบาทอื่นเข้าถึงไม่ได้ | Must |
| FR-6 | ลบ Log อัตโนมัติเมื่อครบ 1 ปี (นับจากเวลาของรายการ) เป็นช่องทางเดียวที่ลบได้ | Must |
| FR-7 | การเปิดดู Log ของ admin ถูกลง Log ด้วย (เหตุการณ์ที่ 10) | Must |
| FR-8 | เมื่อมีการลบข้อมูลส่วนบุคคลตามคำขอ (เช่น ลบข้อความ) ต้องลง Log ว่ามีการลบ โดยไม่เก็บเนื้อหาที่ถูกลง | Must |
| FR-9 | ค้นหา/กรอง Log ตามผู้กระทำ ประเภทเหตุการณ์ ช่วงเวลา ผลลัพธ์ และ ref ID | Should |
| FR-10 | บันทึกเหตุการณ์ล้มเหลว/ถูกปฏิเสธสิทธิ์ (เช่น พยายามเข้าหน้า Log โดยไม่ใช่ admin) | Should |
| FR-11 | ตรวจจับการแก้ไข Log โดยไม่ชอบ (เช่น hash chain/ลายเซ็น) | Could |

### เหตุการณ์ที่ต้องลง Log
| # | กลุ่มเหตุการณ์ | เหตุการณ์ย่อย | ref ID ที่เก็บ (ไม่เก็บเนื้อหา/ค่า) |
|---|----------------|----------------|--------------------------------------|
| 1 | การยืนยันตัวตน | login สำเร็จ, logout, login ไม่สำเร็จ | user ID ที่พยายาม (ถ้าระบุได้) |
| 2 | ดูข้อมูลเกรด/GPA | ดูเกรด/GPA ของนักศึกษา | student ID เจ้าของข้อมูล, รหัสรายวิชา (ไม่เก็บค่าเกรด) |
| 3 | ส่งข้อความแชท | ส่งสำเร็จ/ถูกปฏิเสธ (เช่น ไม่ผ่านเกณฑ์ผู้ส่ง) | message ID (ไม่เก็บเนื้อหา) |
| 4 | ตรวจข้อความ | อนุมัติ, ปฏิเสธ, แก้ป้ายเชิงลบ/ไม่เชิงลบ | message ID, ค่าป้ายเดิม→ใหม่ (ไม่เก็บเหตุผลที่เป็นเนื้อหาข้อความ) |
| 5 | ผู้ตรวจเปิดอ่านข้อความ | เปิดอ่านข้อความในคิวตรวจ | message ID |
| 6 | เปลี่ยนเกณฑ์ | เกณฑ์ความเสี่ยง (threshold), เกณฑ์คัด Mentor | ID ของเกณฑ์, ค่าเดิม→ใหม่ของเกณฑ์ (ค่าเกณฑ์ไม่ใช่ข้อมูลส่วนบุคคล) |
| 7 | เปลี่ยนสิทธิ์ผู้ใช้ | เพิ่ม/ลด/เปลี่ยนบทบาทหรือสิทธิ์ | user ID เป้าหมาย, บทบาทเดิม→ใหม่ |
| 8 | ความยินยอม | ให้ความยินยอม, ถอนความยินยอม | user ID, เวอร์ชันประกาศ |
| 9 | สิทธิเจ้าของข้อมูล | ขอดู, ขอแก้, ขอลบ และผลดำเนินการ | user ID, request ID, ประเภทข้อมูลที่เกี่ยวข้อง |
| 10 | เปิดดู Log | admin เปิด/ค้นหา/กรอง Log | เงื่อนไขการค้นหา |

## 5. Non-functional Requirements
- **ความไม่เปลี่ยนแปลง (integrity):** สิทธิ์ของแอปต่อที่เก็บ Log ต้องเป็นเขียนเพิ่มอย่างเดียว (INSERT only) การลบทำโดยงานเก็บตกตามระยะเก็บเท่านั้น
- **ความเป็นส่วนตัว:** user ID/เวลา/พฤติกรรมการเข้าถึงเป็นข้อมูลส่วนบุคคล จึงอยู่ภายใต้ [[20261015-03-pdpa-baseline|REQ-PDPA]] (ผู้เข้าถึงจำกัด, มีในประกาศความเป็นส่วนตัว, มีระยะเก็บ)
- **ประสิทธิภาพ:** การลง Log ต้องไม่ทำให้การใช้งานหลักช้าอย่างมีนัยสำคัญ (ค่าเป้าหมายยังไม่กำหนด)
- **ความครบถ้วน:** การกระทำที่ล้มเหลวหรือถูกปฏิเสธก็ต้องลง Log

## 6. Business Rules
- ทุกรายการ Log ต้องมีครบ 4 อย่าง: ผู้กระทำ, เวลา, ผลลัพธ์, รหัสอ้างอิง
- Log เก็บ "ว่ามีเหตุการณ์เกิดขึ้น" ไม่เก็บ "เนื้อหา" (ข้อความแชท, ค่าเกรด)
- ไม่มีบทบาทใด (รวม admin) แก้หรือลบ Log ได้ มีเพียงงานลบอัตโนมัติเมื่อครบ 1 ปี
- เฉพาะ admin ดู Log ได้ และดูได้อย่างเดียว
- ทุกฟีเจอร์ต้องระบุเหตุการณ์ที่ลง Log ในสเปกของตน โดยอ้างถึง REQ-AUDIT

## 7. ขอบเขต
- **In scope:** การบันทึก 10 กลุ่มเหตุการณ์, ที่เก็บ Log แบบ append-only, หน้าดู Log สำหรับ admin, ลบอัตโนมัติครบ 1 ปี
- **Out of scope (assumption):** การแจ้งเตือนเรียลไทม์จาก Log (alerting), ส่งออก Log ไประบบ SIEM ภายนอก, การ monitor ประสิทธิภาพระบบ (application log/error log ทั่วไป), การเปิดดู Log โดยเจ้าของข้อมูลเอง (ใช้ช่องทางสิทธิขอดูข้อมูลของ PDPA แทน)

## 8. Acceptance Criteria
- AC-1: ทำแต่ละเหตุการณ์ใน 10 กลุ่ม แล้วพบรายการ Log ที่มีผู้กระทำ เวลา ผลลัพธ์ และ ref ID ครบ
- AC-2: ส่งข้อความแชทและดูเกรด แล้วตรวจ Log ต้องไม่พบเนื้อหาข้อความหรือค่าเกรดในรายการใดเลย (รวมฟิลด์ที่เป็นข้อความอิสระ)
- AC-3: ทดสอบแก้/ลบรายการ Log ผ่าน UI, API และสิทธิ์ของ DB user ของแอป ต้องทำไม่ได้ทุกช่องทาง
- AC-4: นักศึกษา/Mentor/อาจารย์ เข้าหน้า Log ไม่ได้ (ถูกปฏิเสธและมี Log การพยายาม); admin เข้าได้และไม่มีปุ่มแก้/ลบ
- AC-5: รายการ Log อายุเกิน 1 ปีถูกลบอัตโนมัติ และรายการอายุไม่ถึง 1 ปียังอยู่
- AC-6: admin เปิดดู Log แล้วมีรายการเหตุการณ์ "เปิดดู Log" เกิดขึ้น
- AC-7: เมื่อนักศึกษาขอลบข้อความ เนื้อหาถูกลงแต่มีรายการ Log ว่าลบ (มี message ID ไม่มีเนื้อหา)

## 9. Assumptions และคำตอบที่ได้จากผู้ใช้
**คำตอบจากผู้ใช้** (จากรอบถามร่วมกับ REQ-PDPA)
| คำถาม | คำตอบ |
|-------|-------|
| เพิ่มหัวข้อ "ข้อมูลส่วนบุคคล + เหตุการณ์ที่ลง Log" ในสเปกเดิม 2 ฉบับหรือไม่ | เพิ่มหัวข้อสั้น ๆ ทั้ง 2 ฉบับ (ดู REQ-20261014-01, -02) |

**Assumptions**
- "เวลา" เก็บเป็น timestamp พร้อมเขตเวลา (UTC หรือ +07:00 ระบุให้ชัดตอนออกแบบ)
- "ผลลัพธ์" มีอย่างน้อยสำเร็จ/ล้มเหลว และเหตุผลล้มเหลวเป็นรหัส (ไม่ใช่ข้อความอิสระ) เพื่อกันเนื้อหาหลุดเข้า Log
- ค่าเกณฑ์ที่เปลี่ยน (ข้อ 6) บันทึกค่าเดิม→ใหม่ได้ เพราะไม่ใช่ข้อมูลส่วนบุคคลหรือเกรดจริง
- "ลบอัตโนมัติ" ไม่ขัดกับ "ลบไม่ได้" เพราะงานตามระยะเก็บถือเป็นข้อยกเว้นเดียว และงานลบนี้ต้องไม่เปิดให้ผู้ใช้เรียกเอง
- การอ่านข้อความโดยผู้รับที่เป็นนักศึกษาปกติไม่ต้องลง Log (requirement ระบุเฉพาะ "ผู้ตรวจเปิดอ่าน")

## 10. คำถามที่ยังเปิดอยู่
- "เกณฑ์คัด Mentor" และบทบาท Mentor ยังไม่มีในสเปกเดิม (สัมพันธ์กับนิยาม "ผ่านเกณฑ์" ใน REQ-20261014-02) ต้องยืนยันว่าคือเกณฑ์เดียวกันหรือไม่
- หลักฐานการลบข้อมูลใน Log อยู่ 1 ปีแล้วถูกลบ ซึ่งอาจสั้นกว่าที่ต้องการพิสูจน์ต่อสำนักงาน/ผู้ร้องเรียน — ต้องการเก็บยาวกว่านั้นหรือไม่
- รูปแบบเทคนิคการกันแก้ไข (DB permission, WORM storage, hash chain) — ตัดสินใจในเอกสาร design
- Log ของเหตุการณ์ login ไม่สำเร็จเก็บ IP/อุปกรณ์หรือไม่ (IP เป็นข้อมูลส่วนบุคคล)
- ระดับรายละเอียดการ "ดูเกรด": นับทุกครั้งที่เปิดหน้า หรือรวมเป็นช่วง session
- admin หลายคนมีผลต่อ Log การดูของกันและกันอย่างไร (ใครดู Log ของ admin)
