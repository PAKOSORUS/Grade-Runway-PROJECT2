# ระบบติดตามสถานการณ์การเรียนและแจ้งเตือนความเสี่ยง

- **ID:** REQ-20261014-01
- **วันที่:** 2026-10-14
- **สถานะ:** Draft

## 1. ที่มา / Requirement ดิบ
> ระบบที่ช่วยติดตามสถานการณ์การเรียนของนักเรียน/นักศึกษา โดยพิจารณาจากหลายตัวแปรร่วมกัน (เกรด/ผลการเรียน, การเข้าเรียน, การส่งงาน, แนวโน้มผลการเรียน) แล้วแจ้งเตือนผู้เรียนเมื่อเข้าเงื่อนไขที่มีความเสี่ยง พร้อมให้คำแนะนำแนวทางการเรียนที่คำนวณเฉพาะบุคคลจากข้อมูลย้อนหลังของผู้เรียนแต่ละคน

## 2. เป้าหมาย
- ให้ผู้เรียนและครูที่ปรึกษาเห็นสถานการณ์การเรียนจากหลายตัวแปรร่วมกัน
- ตรวจพบความเสี่ยงตั้งแต่เนิ่น ๆ และแจ้งเตือนทันเวลา
- ให้คำแนะนำแนวทางการเรียนที่เฉพาะบุคคล คำนวณจากข้อมูลย้อนหลังของผู้เรียนแต่ละคน

## 3. ผู้ใช้ / บทบาทที่เกี่ยวข้อง
| บทบาท | การใช้งานหลัก |
|-------|----------------|
| ผู้เรียน (นักเรียน/นักศึกษา) | ดูสถานการณ์การเรียนของตน รับแจ้งเตือน และรับคำแนะนำ |
| ครู/อาจารย์ที่ปรึกษา | ดูสถานการณ์และรับแจ้งเตือน (in-app + อีเมล) ของผู้เรียนในที่ปรึกษา พิจารณาคำคัดค้านการประเมินตาม REQ-PDPA |
| ผู้ดูแลระบบ (assumption) | ตั้งค่า threshold และการเชื่อมต่อระบบภายนอก |

## 4. Functional Requirements
| ID | รายละเอียด | Priority (Must/Should/Could) |
|----|------------|------------------------------|
| FR-1 | ดึงข้อมูลเกรด/ผลการเรียน การเข้าเรียน และการส่งงาน จากระบบเดิม (LMS/ระบบทะเบียน) ผ่าน API | Must |
| FR-2 | คำนวณแนวโน้มผลการเรียนของผู้เรียนจากข้อมูลย้อนหลัง | Must |
| FR-3 | ประเมินความเสี่ยงของผู้เรียนจากหลายตัวแปรร่วมกัน ด้วยกฎ threshold ที่ปรับค่าได้ | Must |
| FR-4 | แจ้งเตือนผู้เรียนเมื่อเข้าเงื่อนไขเสี่ยง ผ่านระบบ (in-app) และอีเมล | Must |
| FR-5 | สร้างคำแนะนำแนวทางการเรียนเฉพาะบุคคลจากข้อมูลย้อนหลังของผู้เรียนแต่ละคน | Must |
| FR-6 | แดชบอร์ดสถานการณ์การเรียนสำหรับผู้เรียน | Should |
| FR-7 | ครู/อาจารย์ที่ปรึกษาดูสถานการณ์และการแจ้งเตือนของผู้เรียนในความดูแล | Should |
| FR-8 | ผู้ดูแลระบบตั้งค่า threshold ของกฎความเสี่ยงได้ | Must |
| FR-9 | เก็บประวัติการแจ้งเตือนและคำแนะนำ | Could |
| FR-10 | แจ้งเตือนครู/อาจารย์ที่ปรึกษา ทาง in-app และอีเมล เมื่อผู้เรียนในความดูแลเข้าเงื่อนไขเสี่ยง (อีเมลใช้ข้อความทั่วไปไม่ระบุเกรด/รายละเอียดความเสี่ยง ตาม REQ-PDPA FR-9) | Should |
| FR-11 | ซิงก์ข้อมูลจาก LMS/ทะเบียนและประเมินความเสี่ยงทุกวัน (รอบรายวัน) | Must |

## 5. Non-functional Requirements
- **ความเป็นส่วนตัว:** ข้อมูลผลการเรียนเป็นข้อมูลส่วนบุคคล ผู้เรียนเห็นเฉพาะข้อมูลตน ครูเห็นเฉพาะผู้เรียนในความดูแล (ปฏิบัติตาม [[20261015-03-pdpa-baseline|REQ-PDPA]])
- **ความสามารถอธิบายได้:** การแจ้งเตือนต้องบอกเหตุผลว่าเข้าเงื่อนไขใด
- **ความทันสมัยของข้อมูล:** ซิงก์และประเมินความเสี่ยงวันละครั้ง (FR-11)

## 6. Business Rules
- ความเสี่ยงประเมินจาก 4 ตัวแปร: เกรด/ผลการเรียน, การเข้าเรียน, การส่งงาน, แนวโน้มผลการเรียน
- เงื่อนไขความเสี่ยงเป็นกฎ threshold ปรับค่าได้ โดย admin ค่าเริ่มต้น: GPA < 2.00, การเข้าเรียน < 80%, การส่งงาน < 70% (ใช้ค่าแนะนำ ปรับได้ภายหลัง); เกณฑ์แนวโน้ม "เกรดลดลงต่อเนื่อง N ครั้ง" ยังไม่ได้กำหนด N
- คำแนะนำต้องอิงข้อมูลย้อนหลังของผู้เรียนคนนั้น ไม่ใช่คำแนะนำทั่วไป

## 7. ขอบเขต
- **In scope:** เชื่อมข้อมูลผ่าน API, ประเมินความเสี่ยงด้วยกฎ threshold, แจ้งเตือนผู้เรียนทาง in-app และอีเมล, คำแนะนำเฉพาะบุคคล, มุมมองสำหรับผู้เรียนและครูที่ปรึกษา
- **Out of scope:** โมเดล ML ทำนายความเสี่ยง, แจ้งเตือนผ่าน LINE/Push, การบันทึกข้อมูลเกรด/เข้าเรียนเองในระบบนี้, การแจ้งผู้ปกครอง (assumption ยืนยันภายหลังได้)

## 8. Acceptance Criteria
- AC-1: เมื่อข้อมูลของผู้เรียนเข้าเงื่อนไขเสี่ยงตามกฎที่ตั้งไว้ ผู้เรียนได้รับแจ้งเตือนทั้งใน-app และอีเมล พร้อมเหตุผล
- AC-2: เมื่อผู้ดูแลระบบเปลี่ยนค่า threshold การประเมินรอบถัดไปใช้ค่าใหม่
- AC-3: ผู้เรียนแต่ละคนได้คำแนะนำที่ต่างกันตามข้อมูลย้อนหลังของตน
- AC-4: ผู้เรียนเห็นเฉพาะข้อมูลของตน ครูที่ปรึกษาเห็นเฉพาะผู้เรียนในความดูแล
- AC-5: ข้อมูลจาก LMS/ระบบทะเบียนถูกดึงผ่าน API และสะท้อนในการประเมินความเสี่ยง
- AC-6: เมื่อผู้เรียนเข้าเงื่อนไขเสี่ยง อาจารย์ที่ปรึกษาได้รับแจ้งทั้ง in-app และอีเมล โดยอีเมลไม่มีเกรด/รายละเอียดความเสี่ยง
- AC-7: การซิงก์และประเมินความเสี่ยงทำงานทุกวัน

## 9. Assumptions และคำตอบที่ได้จากผู้ใช้
**คำตอบจากผู้ใช้**
| คำถาม | คำตอบ |
|-------|-------|
| แหล่งข้อมูล | เชื่อมระบบเดิม (LMS/ระบบทะเบียน) ผ่าน API |
| บทบาทผู้ใช้ | ผู้เรียน + ครู/อาจารย์ที่ปรึกษา |
| เงื่อนไขความเสี่ยง | กฎ threshold ปรับค่าได้ |
| ช่องทางแจ้งเตือน | In-app + อีเมล |
| ระบบเดิมและระดับผู้เรียน | ระดับมหาวิทยาลัย ระบบเดิมมี API พร้อมใช้ |
| ครูที่ปรึกษารับแจ้งเตือนหรือไม่ | แจ้งด้วย (in-app + อีเมล) |
| ความถี่ประเมิน/ซิงก์ | ทุกวัน |
| threshold เริ่มต้น | ใช้ค่าแนะนำ (GPA < 2.00, เข้าเรียน < 80%, ส่งงาน < 70%) |
| ระยะเก็บข้อมูลเกรดที่ซิงก์ | ตลอดสถานภาพนักศึกษา |

**Assumptions**
- มีบทบาทผู้ดูแลระบบสำหรับตั้งค่า threshold และการเชื่อมต่อ
- "คำแนะนำเฉพาะบุคคล" สร้างด้วยกฎ/สถิติจากข้อมูลย้อนหลังของผู้เรียน (ไม่ใช้ ML ในเฟสนี้ ตามแนวทาง threshold)
- ผู้เรียนต้องมีข้อมูลย้อนหลังเพียงพอจึงจะคำนวณแนวโน้มและคำแนะนำได้ (ผู้เรียนใหม่ใช้เฉพาะกฎพื้นฐาน)

## 10. คำถามที่ยังเปิดอยู่
ตอบแล้ว (ดูข้อ 9): ระดับผู้เรียน (มหาวิทยาลัย), มี API, ความถี่รายวัน, threshold เริ่มต้น, แจ้งอาจารย์ที่ปรึกษา, ระยะเก็บเกรด (ตลอดสถานภาพ ตาม [[20261015-03-pdpa-baseline|REQ-20261015-03]])

ยังเปิดอยู่:
- ชื่อ/ยี่ห้อ LMS และทะเบียน รูปแบบ API และวิธีขอสิทธิ์เข้าถึง (ต้องรู้ก่อนออกแบบการเชื่อมต่อ)
- ค่า N ของเกณฑ์ "เกรดลดลงต่อเนื่อง N ครั้ง" และตรวจค่า threshold เริ่มต้นกับข้อมูลจริงก่อนใช้งาน

## 12. ข้อมูลส่วนบุคคลและเหตุการณ์ที่ลง Log (เพิ่ม 2026-10-15)
**ข้อมูลส่วนบุคคลที่ฟีเจอร์เก็บ (อ้างถึง [[20261015-03-pdpa-baseline|REQ-PDPA]])**
- เกรด/GPA, การเข้าเรียน, การส่งงาน, แนวโน้มผลการเรียน (ข้อมูลอ่อนไหวด้านการศึกษา — ซิงก์จาก LMS/ทะเบียน)
- ผลประเมินความเสี่ยงและประวัติการแจ้งเตือน/คำแนะนำรายบุคคล (FR-9)
- อีเมล/ตัวระบุผู้ใช้ สำหรับส่งแจ้งเตือน
- ระยะเก็บ: ผลประเมิน/ประวัติแจ้งเตือน ตลอดสถานภาพนักศึกษา แล้วลบหรือทำให้ไม่ระบุตัวตน (ค่าตั้งต้น รอยืนยัน) ดูตารางใน REQ-PDPA

**เหตุการณ์ที่ต้องลง Log (อ้างถึง [[20261015-01-audit-logging|REQ-AUDIT]])**
- ดูเกรด/GPA ของนักศึกษา (เหตุการณ์ #2) รวมการที่ครู/อาจารย์ที่ปรึกษาดูผู้เรียนในความดูแล (FR-7)
- admin เปลี่ยนเกณฑ์ความเสี่ยง/threshold (#6)
- เปลี่ยนสิทธิ์ครู/ที่ปรึกษา (#7), ขอดู/แก้/ลบข้อมูลของตน (#9)
- Log ไม่เก็บค่าเกรดจริง เก็บเพียง student ID และรหัสรายวิชา
