# ช่องแชทแนะนำแนวทางการเรียนระหว่างนักศึกษา (Peer Advice Chat)

- **ID:** REQ-20261014-02
- **วันที่:** 2026-10-14
- **สถานะ:** Draft

## 1. ที่มา / Requirement ดิบ
> Grade Runway ต้องมีช่องแชทให้นักศึกษาส่งข้อความแนะนำแนวทางการเรียนให้นักศึกษาคนอื่นที่ต้องการพัฒนาตนเอง
> ผู้ส่งต้องเป็น: [ยังไม่กำหนด: นักศึกษาทุกคน / เฉพาะผู้ผ่านเกณฑ์]
> ทุกข้อความต้องผ่านการอนุมัติก่อนผู้รับจะเห็น
> ทุกข้อความต้องมีการระบุว่า "เชิงลบ" หรือ "ไม่เชิงลบ" ก่อนอนุมัติ โดยผู้กำหนดคือ [ยังไม่กำหนด: ผู้ส่ง / ระบบ / ผู้ตรวจ]
> ข้อความเชิงลบต้อง [ยังไม่กำหนด: ถูกปฏิเสธ / ผู้ตรวจตัดสินใจ]
> อาจารย์และ admin ต้องเป็นผู้ตรวจและอนุมัติข้อความ [ยังไม่กำหนด: คนใดคนหนึ่ง / ทั้งสองบทบาท]
> เมื่อข้อความถูกปฏิเสธ ผู้ส่งต้องได้รับแจ้งพร้อมเหตุผล

## 2. เป้าหมาย
- ให้นักศึกษาที่ผ่านเกณฑ์แบ่งปันแนวทางการเรียนให้เพื่อนที่ต้องการพัฒนาตนเอง
- คุมคุณภาพและความปลอดภัยของเนื้อหาด้วยการตรวจและอนุมัติก่อนเผยแพร่ โดยเฉพาะข้อความเชิงลบ

## 3. ผู้ใช้ / บทบาทที่เกี่ยวข้อง
| บทบาท | การใช้งานหลัก |
|-------|----------------|
| นักศึกษาผู้ส่ง (ผ่านเกณฑ์ GPA ≥ 3.25 = Mentor) | ส่งข้อความแนะนำแบบนิรนาม รับแจ้ง in-app เมื่ออนุมัติ/ปฏิเสธ (พร้อมเหตุผล) แก้แล้วส่งใหม่ได้ |
| นักศึกษาผู้รับ (ระบบจับคู่อัตโนมัติ) | อ่านข้อความที่ผ่านการอนุมัติแล้วเท่านั้น ไม่เห็นชื่อผู้ส่ง |
| อาจารย์ (ผู้ตรวจ) | ระบุเชิงลบ/ไม่เชิงลบ และอนุมัติหรือปฏิเสธข้อความ |
| Admin (ผู้ตรวจ) | สิทธิ์เดียวกับอาจารย์ในการตรวจและอนุมัติ |
| AI (ตัวช่วย ไม่บังคับ) | **เลื่อน ไม่ใช้ในเฟสแรก** — ช่วยวิเคราะห์ว่าข้อความเชิงลบหรือไม่ เพื่อเสนอให้ผู้ตรวจ |

## 4. Functional Requirements
| ID | รายละเอียด | Priority (Must/Should/Could) |
|----|------------|------------------------------|
| FR-1 | ช่องแชทให้นักศึกษาที่ผ่านเกณฑ์ส่งข้อความแนะนำแนวทางการเรียนถึงนักศึกษาคนอื่น | Must |
| FR-2 | ข้อความทุกข้อความเข้าสถานะรออนุมัติ และผู้รับมองไม่เห็นจนกว่าจะอนุมัติ | Must |
| FR-3 | ผู้ตรวจ (อาจารย์/admin) ต้องระบุ "เชิงลบ" หรือ "ไม่เชิงลบ" ให้ข้อความก่อนอนุมัติ | Must |
| FR-4 | ผู้ตรวจ (อาจารย์/admin) อนุมัติหรือปฏิเสธข้อความได้ ทั้งสองบทบาทมีสิทธิ์เท่ากัน | Must |
| FR-5 | ข้อความเชิงลบให้ผู้ตรวจตัดสินใจว่าจะอนุมัติหรือปฏิเสธ | Must |
| FR-6 | เมื่อปฏิเสธ ต้องกรอกเหตุผล และแจ้งผู้ส่งพร้อมเหตุผล | Must |
| FR-7 | ตรวจสอบสิทธิ์ผู้ส่งตามเกณฑ์ "ผู้ผ่านเกณฑ์" = GPA ≥ 3.25 จากทะเบียน/LMS (เกณฑ์เดียวกับเกณฑ์คัด Mentor ปรับค่าได้โดย admin) ก่อนอนุญาตให้ส่ง | Must |
| FR-8 | AI วิเคราะห์ข้อความและเสนอผลเชิงลบ/ไม่เชิงลบให้ผู้ตรวจยืนยัน (ผู้ตรวจตัดสินขั้นสุดท้าย) — **เลื่อน: ไม่ทำในเฟสแรก** | Could (Deferred) |
| FR-9 | กันตรวจซ้ำ: ข้อความที่ผู้ตรวจคนหนึ่งกำลังตรวจหรือตัดสินแล้วต้องไม่ถูกตัดสินซ้ำโดยอีกคน | Should |
| FR-10 | ระบบจับคู่ผู้รับอัตโนมัติ: จับคู่ข้อความกับนักศึกษาที่ต้องการพัฒนาตนเอง (เช่น ผู้ที่ถูกแจ้งเตือนความเสี่ยงใน REQ-20261014-01) กติกาจับคู่ละเอียดกำหนดใน design | Must |
| FR-11 | ผู้ส่งเป็นนิรนามต่อผู้รับ (ผู้รับไม่เห็นชื่อ/ตัวระบุผู้ส่ง) ผู้ตรวจและ Log ยังระบุผู้ส่งได้ผ่านรหัสอ้างอิง | Must |
| FR-12 | แจ้งผู้ส่งแบบ in-app เมื่อข้อความถูกอนุมัติ (นอกเหนือจากแจ้งเมื่อถูกปฏิเสธใน FR-6) | Should |
| FR-13 | ผู้ส่งแก้ไขแล้วส่งใหม่หลังถูกปฏิเสธได้ไม่จำกัดจำนวนครั้ง โดยข้อความใหม่เข้าคิวรออนุมัติเหมือนข้อความทั่วไป | Should |
| FR-14 | SLA ผู้ตรวจ 3 วัน: ข้อความที่ค้างรออนุมัติเกิน 3 วันให้แจ้งเตือนผู้ตรวจ (อาจารย์/admin) | Should |

## 5. Non-functional Requirements
- **ความปลอดภัยของเนื้อหา:** ผู้รับต้องไม่เห็นข้อความที่ยังไม่อนุมัติหรือถูกปฏิเสธ ไม่ว่าทางใด
- **ความรับผิดชอบ:** เก็บประวัติว่าใครตรวจ ผลที่ตัดสิน การระบุเชิงลบ/ไม่เชิงลบ และเหตุผล (audit trail)
- **ความเป็นส่วนตัว:** ต้องกำหนดว่าข้อความแสดงชื่อผู้ส่งหรือไม่ (ดูข้อ 10)

## 6. Business Rules
- ผู้ส่งต้องเป็นนักศึกษาที่ผ่านเกณฑ์เท่านั้น
- ทุกข้อความต้องผ่านการอนุมัติก่อนผู้รับเห็น ไม่มีข้อยกเว้น
- ต้องระบุเชิงลบ/ไม่เชิงลบก่อนอนุมัติเสมอ ผู้ระบุคือผู้ตรวจ (AI ช่วยแนะนำได้แต่ผู้ตรวจยืนยัน)
- ข้อความเชิงลบ: ผู้ตรวจตัดสินใจอนุมัติหรือปฏิเสธเอง (ไม่ปฏิเสธอัตโนมัติ)
- อาจารย์และ admin อนุมัติได้ทั้งคู่ ใช้สิทธิ์เดียวกัน
- การปฏิเสธต้องมีเหตุผลเสมอ และผู้ส่งต้องได้รับแจ้ง

## 7. ขอบเขต
- **In scope:** ส่งข้อความ, คิวรออนุมัติ, ระบุเชิงลบ/ไม่เชิงลบ, อนุมัติ/ปฏิเสธ, แจ้งผู้ส่งเมื่อถูกปฏิเสธพร้อมเหตุผล, แสดงเฉพาะข้อความที่อนุมัติแก่ผู้รับ
- **In scope (เพิ่ม):** จับคู่ผู้รับอัตโนมัติ, ผู้ส่งนิรนามต่อผู้รับ, แจ้งผู้ส่งแบบ in-app เมื่ออนุมัติ/ปฏิเสธ, ส่งใหม่หลังถูกปฏิเสธ, SLA ผู้ตรวจ 3 วัน
- **Out of scope (assumption):** การแชทตอบโต้แบบ real-time, ไฟล์/รูปแนบ, การรายงานข้อความโดยผู้รับ, AI วิเคราะห์ข้อความ (เลื่อนจากเฟสแรก)

## 8. Acceptance Criteria
- AC-1: นักศึกษาที่ไม่ผ่านเกณฑ์ส่งข้อความไม่ได้
- AC-2: ข้อความที่ส่งใหม่อยู่สถานะรออนุมัติ และผู้รับไม่เห็น
- AC-3: ผู้ตรวจอนุมัติข้อความที่ยังไม่ระบุเชิงลบ/ไม่เชิงลบไม่ได้
- AC-4: อาจารย์และ admin เข้าคิวตรวจและอนุมัติ/ปฏิเสธได้เหมือนกัน
- AC-5: ข้อความเชิงลบไม่ถูกปฏิเสธอัตโนมัติ ต้องรอผู้ตรวจตัดสิน
- AC-6: ปฏิเสธโดยไม่ใส่เหตุผลไม่ได้ และผู้ส่งได้รับแจ้งพร้อมเหตุผลนั้น
- AC-7: ผู้รับเห็นเฉพาะข้อความที่อนุมัติแล้ว
- AC-8: ผู้รับไม่เห็นชื่อ/ตัวระบุผู้ส่ง ส่วนผู้ตรวจและ Log ระบุผู้ส่งได้
- AC-9: นักศึกษา GPA < 3.25 ส่งไม่ได้ GPA ≥ 3.25 ส่งได้ (ใช้ค่าเกณฑ์เดียวกับ Mentor)
- AC-10: ผู้ส่งได้รับแจ้ง in-app เมื่ออนุมัติและเมื่อปฏิเสธ และส่งข้อความใหม่หลังถูกปฏิเสธได้ (เข้าคิวรออนุมัติ)
- AC-11: ข้อความรออนุมัติเกิน 3 วัน ผู้ตรวจได้รับแจ้งเตือน
- AC-12: ข้อความที่อนุมัติถูกจับคู่ถึงผู้รับโดยระบบ ไม่ต้องเลือกผู้รับเอง

## 9. Assumptions และคำตอบที่ได้จากผู้ใช้
**คำตอบจากผู้ใช้**
| คำถาม | คำตอบ |
|-------|-------|
| ใครส่งข้อความได้ | เฉพาะนักศึกษาที่ผ่านเกณฑ์ |
| ใครระบุเชิงลบ/ไม่เชิงลบ | ผู้ตรวจ (อาจารย์/admin) หรืออาจมี AI เข้ามาช่วยวิเคราะห์ |
| ข้อความเชิงลบจัดการอย่างไร | ผู้ตรวจตัดสินใจ |
| อาจารย์/admin ใครอนุมัติได้ | ทั้งสองบทบาท |
| "ผ่านเกณฑ์" = เกณฑ์เดียวกับ Mentor หรือไม่ | ใช่ Mentor = ผู้ผ่านเกณฑ์ ใช้ GPA ขั้นต่ำ 3.25 จากทะเบียน/LMS |
| ผู้รับคือใคร | ระบบจับคู่อัตโนมัติ |
| แสดงชื่อผู้ส่งหรือไม่ | นิรนามต่อผู้รับ |
| แจ้งผู้ส่งเมื่ออนุมัติ | แจ้งทาง in-app |
| แก้แล้วส่งใหม่หลังถูกปฏิเสธ | ได้ ไม่จำกัด |
| SLA ผู้ตรวจ | 3 วัน แล้วแจ้งเตือนผู้ตรวจ |
| ใช้ AI หรือไม่ | ไม่ใช้ในเฟสแรก |

**Assumptions**
- "AI ช่วยวิเคราะห์" (FR-8) เลื่อนไปหลังเฟสแรก ผู้ตรวจระบุเชิงลบ/ไม่เชิงลบเอง หากเปิดใช้ภายหลังต้องแจ้งใน privacy notice และตรวจการส่งข้อมูลนอกระบบ/ต่างประเทศ (REQ-PDPA)
- "ผ่านเกณฑ์" = GPA ≥ 3.25 จากข้อมูลทะเบียน/LMS ที่ซิงก์ไว้ (ค่า 3.25 ปรับได้ และเปลี่ยนค่าลง Log เหตุการณ์ #6)
- จับคู่อัตโนมัติ: assumption ว่าจับคู่กับนักศึกษาที่ถูกแจ้งเตือนความเสี่ยง ข้อกำหนดละเอียดอยู่ในเอกสาร design
- ผู้ส่งนิรนามเฉพาะต่อผู้รับ ผู้ตรวจ admin และ Log ระบุผู้ส่งได้ (จำเป็นต่อการตรวจสอบและ PDPA)
- ส่งใหม่ไม่จำกัดครั้ง จึงยังไม่มีการจำกัดอัตราการส่งซ้ำ (ดูข้อ 10)
- ข้อความเป็นแบบส่งแล้วรอตรวจ ไม่ใช่การสนทนา real-time

## 10. คำถามที่ยังเปิดอยู่
ตอบแล้ว (ดูข้อ 9): นิยามผ่านเกณฑ์/Mentor, ผู้รับ, ชื่อผู้ส่ง, การแจ้งผู้ส่ง, ส่งใหม่, SLA, AI

ยังเปิดอยู่:
- กติกาการจับคู่อัตโนมัติ: จับคู่กับใคร กี่คนต่อข้อความ และเกณฑ์ผู้ต้องการพัฒนาตนเอง (ตัดสินใจใน design)
- การจำกัดอัตราการส่งซ้ำ เมื่อส่งใหม่ได้ไม่จำกัด (กันสแปมเข้าคิวตรวจ)
- ข้อความที่ค้างเกิน 3 วันหลังแจ้งเตือนผู้ตรวจแล้ว ต้อง escalate ต่อหรือไม่
- หาก admin ที่เหลือมีคนเดียว/ผู้ตรวจไม่ครบ SLA จัดการอย่างไร

## 12. ข้อมูลส่วนบุคคลและเหตุการณ์ที่ลง Log (เพิ่ม 2026-10-15)
**ข้อมูลส่วนบุคคลที่ฟีเจอร์เก็บ (อ้างถึง [[20261015-03-pdpa-baseline|REQ-PDPA]])**
- เนื้อหาข้อความแชท (อาจมีข้อมูลส่วนตัว/ผลการเรียนของผู้ส่ง), ตัวระบุผู้ส่ง, เวลาส่ง
- ผลตรวจ: ป้ายเชิงลบ/ไม่เชิงลบ, ผู้ตรวจ, เหตุผลการปฏิเสธ
- ระยะเก็บ: ข้อความอนุมัติแล้ว → ถึงสิ้นปีการศึกษาที่อนุมัติ; ข้อความถูกปฏิเสธ → 90 วันนับจากวันปฏิเสธ แล้วลบอัตโนมัติ
- สิทธิขอลบ: ผู้ส่งขอลบข้อความได้ ระบบลบเนื้อหาแต่คง Log ว่ามีการลบ
- ถ้าใช้ AI (FR-8) ต้องระบุในประกาศความเป็นส่วนตัวว่าข้อความถูกส่งให้ AI

**เหตุการณ์ที่ต้องลง Log (อ้างถึง [[20261015-01-audit-logging|REQ-AUDIT]])**
